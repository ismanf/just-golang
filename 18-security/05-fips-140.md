# FIPS 140 — Native FIPS Mode (Go 1.24+)

## TL;DR

For Go's first 15 years, "FIPS-compliant Go" meant one of: (a) the **BoringCrypto** patchset maintained out-of-tree by Google, requiring the `boringcrypto` build tag and CGo on Linux/amd64 only; (b) Microsoft's **microsoft/go** fork piping `crypto/*` through OpenSSL/SymCrypt via CGo; or (c) a vendor distribution like **RHEL's Go**. None of these were officially supported by the upstream Go team. **Go 1.24 changed that.** It shipped a **native FIPS 140-3 module** — written in pure Go, validated under NIST's Cryptographic Module Validation Program (CMVP), and selected at runtime via the `GOFIPS140` environment variable. Go 1.26 makes the module the default for FIPS-required builds, adds support for ML-KEM and ML-DSA within the validated boundary, and stabilises the `crypto/internal/fips140` package layout. The single biggest gotcha: turning on FIPS mode **disables** any algorithm the validated module doesn't cover — including some you currently use (X25519 pre-1.26, ChaCha20-Poly1305, Ed25519, BLAKE2, SHA-3 in some Go versions). Read the algorithm list before flipping the switch in production.

## Mental Model

```
                  Your application
                  ────────────────
                       │
                       │ crypto/aes.NewCipher, crypto/sha256.Sum256,
                       │ crypto/ecdsa.Sign, ...
                       ▼
   ┌──────────────────────────────────────────────────────┐
   │  Public crypto/* API surface (unchanged)              │
   ├──────────────────────────────────────────────────────┤
   │  Dispatcher  ───►  if GOFIPS140 == "on":              │
   │                       use crypto/internal/fips140      │
   │                       (validated module — restricted   │
   │                        algo set, self-tested at init)  │
   │                    else:                               │
   │                       use the standard implementation  │
   └──────────────────────────────────────────────────────┘
```

The validated module is a *subset* of the standard library's crypto, with three constraints layered on top:

1. **Algorithm allow-list** — only NIST-approved primitives.
2. **Self-tests at init** — module runs known-answer tests (KATs) on startup and refuses to start if any fail.
3. **Integrity check** — the module verifies its own bytes haven't been modified post-build.

## What Counts as a FIPS-Validated Module

NIST's CMVP issues a **certificate** for a specific module at a specific version on specific operating environments. The certificate is the legal/compliance artifact. Go's native module receives a certificate from NIST per Go release; the certificate references:

- The exact Go version.
- The exact build configuration.
- The tested operating environments (e.g., RHEL 9 on x86_64, Ubuntu 22.04 on arm64).

You are "running FIPS-validated Go" only if all three match.

## Enabling FIPS Mode (1.24+)

Two orthogonal knobs:

```bash
# At BUILD time — toolchain flag
GOFIPS140=v1.0.0 go build ./...

# At RUN time — env var
GOFIPS140=on ./mybin
```

`GOFIPS140` values:

| Value | Meaning |
|-------|---------|
| `off` (or unset) | FIPS mode disabled. The non-validated, faster implementations run. |
| `on` | FIPS mode enabled. The validated module runs; non-approved algorithms return errors or panic. |
| `only` | Strictest. Like `on`, but **import-time** error if your binary references any non-approved primitive. |
| `v1.0.0` (or other version) | Pin to a specific validated module version at build time. |

At runtime, your program can check:

```go
import "crypto/fips140"

if fips140.Enabled() {
    // running in FIPS mode
}
```

## Algorithm Allow-List

The set is small and changes per Go release. As of 1.26:

**Symmetric**
- AES-128 / AES-192 / AES-256 (ECB, CBC, CTR, GCM, GCM-SIV, KW, KWP)
- TDES (legacy, for decrypt only)

**Hash**
- SHA-1 (legacy use only — non-cryptographic)
- SHA-2: SHA-224/256/384/512/512_224/512_256
- SHA-3: SHA3-224/256/384/512, SHAKE128/256

**MAC**
- HMAC with any approved hash
- CMAC-AES, GMAC

**Signatures**
- RSA (PKCS#1 v1.5 and PSS) — keys ≥2048 bits
- ECDSA on P-256/P-384/P-521
- Ed25519 (added 1.25)
- ML-DSA-44/65/87 (added 1.26)

**Key exchange / KEM**
- ECDH P-256/P-384/P-521
- X25519 (added 1.25)
- ML-KEM-512/768/1024 (added 1.24)

**KDF**
- HKDF-SHA-256/384/512
- PBKDF2-SHA-256/384/512
- TLS 1.2/1.3 KDFs (within the TLS stack)

**RNG**
- Hash-DRBG (SP 800-90A) seeded from OS entropy

**Disallowed (return error or panic in FIPS mode)**
- ChaCha20-Poly1305 (not FIPS-approved)
- BLAKE2/BLAKE3
- Salsa20
- RC4, DES (single-key), Blowfish, RIPEMD
- MD5 (allowed within TLS RSA key exchange only, for legacy interop)
- SHA-1 for new signatures (allowed only for legacy verification)

If your code calls a disallowed primitive at runtime in FIPS mode, behaviour depends on the API:

```go
aead, err := chacha20poly1305.New(key)
// err: "fips140: chacha20poly1305 not allowed"
```

If your code calls a disallowed primitive at *import time* in FIPS-`only` mode, the binary won't link.

## Self-Tests at Startup

When `GOFIPS140=on` (or `only`), the runtime executes Known-Answer Tests (KATs) for each algorithm during `init()`. A failure terminates the process with an unambiguous panic before any user code runs:

```
fatal error: FIPS 140 self-test failed: AES-256-GCM
```

This is by design — a module that fails self-test is considered untrustworthy.

You can observe the KAT progression with `GODEBUG=fips140=debug`.

## Integrity Self-Check

The validated module ships with an embedded HMAC-SHA-256 of its own machine code. At init, it recomputes the HMAC and compares; mismatch → panic. This catches:

- Binary patching post-build.
- Bit-rot on disk.
- ASLR/relocation bugs that overwrote module code (extremely rare, but it's part of the FIPS requirement).

## Building a FIPS-Compliant Binary

```bash
# Reproducible build with a specific FIPS module version
GOFIPS140=v1.0.0 \
GOFLAGS='-trimpath -ldflags="-s -w"' \
go build -o myapp ./cmd/myapp

# Run with FIPS mode enforced
GOFIPS140=on ./myapp
```

CI tip: cache `$GOFIPS140` and the build cache; rebuild the binary whenever you bump Go versions, even patch releases — the validated boundary is per-version.

## Verifying at Runtime

```go
import (
    "crypto/fips140"
    "fmt"
    "log"
)

func main() {
    fmt.Printf("FIPS version: %s\n", fips140.Version())
    fmt.Printf("FIPS enabled: %v\n", fips140.Enabled())
    if !fips140.Enabled() {
        log.Fatal("compliance violation: FIPS mode not enabled")
    }
    // ... rest of program
}
```

Use this as a startup gate in regulated deployments. If the operator forgot to set `GOFIPS140=on`, fail fast.

## What FIPS Mode Does NOT Cover

- **TLS configuration.** FIPS mode forces approved primitives, but you still must configure `MinVersion: tls.VersionTLS12` (or 1.3), disable export ciphers, etc.
- **Application logic.** FIPS doesn't protect you from leaking keys in logs.
- **Key generation source.** FIPS requires NIST-approved DRBG; Go's RNG is seeded from `getrandom(2)` on Linux. If you bypass it (read `/dev/urandom` directly, use `math/rand`), you're outside the boundary.
- **Operating environment.** Your kernel and entropy sources matter for full compliance with the CMVP certificate.
- **Container compliance.** Running a FIPS-validated Go binary inside an Alpine container does not make the container FIPS-validated; you also need a FIPS-validated libc/kernel pair.

## Pre-1.24 Alternatives (Legacy)

For pre-1.24 codebases:

### Google BoringCrypto

```bash
GOEXPERIMENT=boringcrypto go build ./...
```

Requires linux/amd64 (or linux/arm64 since Go 1.20+), CGo, and a BoringSSL-compatible toolchain. The validated module is BoringSSL's FIPS module. Effectively unmaintained for new code now that native FIPS exists.

### Microsoft/go

Microsoft's Go fork (https://github.com/microsoft/go) integrates with OpenSSL on Linux and CNG/SymCrypt on Windows. Used heavily inside Azure and some government deployments. Compatibility with upstream Go API is exact; CGo overhead is the main downside.

### RedHat go-toolset

RHEL ships a Go that links to OpenSSL's FIPS module. Pulled automatically when you install `go-toolset` on a FIPS-enabled RHEL. Used by OpenShift.

For new code on Go 1.24+: skip these. Use native FIPS unless you have a hard interop requirement.

## Migrating to FIPS Mode — Checklist

1. **Inventory algorithms.** Grep your codebase for `chacha20poly1305`, `blake2`, `salsa20`, `rc4`, `md5`, raw `sha1.Sum` for crypto. Each is a flag.
2. **Run with `GOFIPS140=only`** in tests. The import-time check surfaces banned primitives that conditional logic would otherwise hide.
3. **Replace primitives:**
   - ChaCha20-Poly1305 → AES-256-GCM (if AES-NI available, faster anyway).
   - BLAKE2/BLAKE3 → SHA-256.
   - Ed25519 (pre-1.25) → ECDSA P-256 (post-1.25 Ed25519 is approved).
4. **Replace third-party crypto libraries.** Many wrap non-approved primitives — `nacl/box`, `nacl/secretbox`, custom AEAD wrappers.
5. **Update TLS curve preferences.** Drop X25519 if pre-1.25; keep P-256/P-384.
6. **Add startup verification** (`fips140.Enabled()` check).
7. **Document the version of the validated module** in your release notes.
8. **Run the test suite under FIPS mode** in CI as a separate matrix.

## TLS Under FIPS

```go
cfg := &tls.Config{
    MinVersion: tls.VersionTLS12,
    CipherSuites: []uint16{
        tls.TLS_AES_256_GCM_SHA384,            // TLS 1.3
        tls.TLS_AES_128_GCM_SHA256,            // TLS 1.3
        tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
        tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
        tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
        tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
    },
    CurvePreferences: []tls.CurveID{
        tls.CurveP384,
        tls.CurveP256,
        // X25519 added to FIPS in Go 1.25
    },
}
```

In FIPS mode, the Go TLS stack will refuse to negotiate a non-approved suite even if the peer advertises it.

## Anti-Patterns & Gotchas

**Assuming `GOFIPS140=on` magically makes your app compliant.** It changes algorithm dispatch. Compliance requires a validated *and* matched-version binary, NIST-listed operating environment, key-management procedures, and audit trail.

**Mixing `crypto/*` with third-party `golang.org/x/crypto/*` primitives.** The latter is *not* part of the validated module. `x/crypto/chacha20poly1305`, `x/crypto/blake2b`, etc. won't be blocked by FIPS mode — they bypass the boundary entirely.

**Using BoringCrypto + native FIPS in the same build.** Only one can be active. Pick.

**Forgetting that `GOFIPS140=on` is a runtime flag.** Production deployments must set it in their unit file / Dockerfile. CI tests of the same binary in non-FIPS mode prove nothing.

**Bypassing `crypto/rand.Reader`** and reading `/dev/urandom` directly. Outside the validated RNG path.

**Calling `crypto/sha1.New()` for HMAC over a TLS session.** Even though SHA-1 is in the approved list as legacy, HMAC-SHA-1 in new code is discouraged. Use SHA-256.

**Using `Ed25519` on Go 1.24 (not 1.25).** Ed25519 was added to the validated module in 1.25. Older builds will panic.

**Shipping a binary built with `GOFIPS140=v1.0.0`** but running it on a non-FIPS-listed kernel. CMVP certifies the binary *and* its host.

**Believing the panic on KAT failure is recoverable.** It is not — the module refuses to operate. Plan deployments to detect this and avoid restart loops (PR/Crash budget alerts).

**Putting compliance check after startup work.** `fips140.Enabled()` should be the second statement in `main()`, before opening DB connections or sockets.

**Caching keys across FIPS-mode toggles.** A binary that ran under FIPS and was restarted in non-FIPS mode may have key material in a non-validated cache. Treat the boundary as one-way: start in FIPS and stay there.

## Performance Notes

FIPS-mode primitives are the same Go implementations; FIPS does not introduce CGo overhead the way BoringCrypto did. Expected impacts:

- **AES-256-GCM**: identical performance (same AES-NI path).
- **SHA-256**: identical.
- **HMAC-SHA-256**: identical.
- **ChaCha20-Poly1305**: unavailable in FIPS mode; if your protocol required it, you're now using AES-GCM (faster on AES-NI, slower on AES-NI-free ARM).
- **RNG**: SP 800-90A Hash-DRBG is slightly slower than the non-FIPS RNG (~5–10% per call). Usually irrelevant.
- **Self-test cost** at startup: ~10–100 ms once per process. Don't fork-and-restart in hot loops.
- **Integrity check** at startup: ~5–20 ms. One-time.

## How Big Companies Use It

- **U.S. federal contractors** mandate FIPS 140 for any "cryptographic module used to protect sensitive but unclassified information" (FedRAMP, FISMA, NIST 800-53). Go 1.24's native module removed a long-standing barrier to using upstream Go in these deployments.
- **Microsoft Azure** (microsoft/go) historically used OpenSSL-backed builds; Azure has begun migration plans toward native FIPS for new Go services.
- **Red Hat OpenShift** uses RHEL's `go-toolset` for FIPS deployments; native FIPS is the announced direction.
- **Google Cloud** Confidential VMs, Assured Workloads, and government regions require FIPS-validated TLS and have piloted native Go FIPS in 1.25+.
- **HashiCorp Vault** ships a FIPS-Inside build using BoringCrypto historically; 1.16+ supports the native module.
- **CockroachDB Enterprise** has a FIPS variant using native FIPS since Go 1.24.
- **Tailscale** does not run FIPS — uses WireGuard primitives (Curve25519, ChaCha20-Poly1305) which are not FIPS-approved.
- **Cloudflare** runs FIPS for FedRAMP-bounded products only; mainline edge uses non-FIPS for full algorithm agility (PQ hybrid, ChaCha20-Poly1305 for mobile).

## Exercises / Self-Check

1. Build a tiny app that prints `crypto/fips140.Enabled()`. Run it with `GOFIPS140=off`, `=on`, and `=only`. Observe.
2. In a FIPS-mode binary, call `golang.org/x/crypto/chacha20poly1305.New(key)`. Observe (the `x/crypto` package is NOT validated; the call may succeed but is outside the boundary).
3. Use `GOFIPS140=only` at build time on a project that imports `nacl/box`. Note the import-time error.
4. Replace `ed25519.Sign` with `ecdsa.SignASN1` (P-256). Benchmark before/after. Decide which to use given your performance budget.
5. Configure a TLS server in FIPS mode. Use `openssl s_client` to negotiate. Confirm only approved suites are offered.
6. Cause a KAT failure deliberately by modifying a byte of the binary's `.text` section in a copy. Run; observe the integrity-check panic.
7. Add a startup check that fails the process if `fips140.Enabled() == false` and the env says it should be on. Wire to your healthcheck.
8. Document your FIPS validation: Go version, module version, operating environment, NIST certificate number. Include in your release notes for the regulated customer.
