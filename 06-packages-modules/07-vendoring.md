# Vendoring — When It Still Matters

## TL;DR

**Vendoring** copies every dependency's source into a `vendor/` directory inside your module, committed to version control. The Go tool builds against `vendor/` instead of the module cache, making the build fully self-contained and offline-reproducible. `go mod vendor` generates `vendor/` from your `go.mod`; `vendor/modules.txt` is the manifest. Vendoring is **not the default** since modules (1.11+), but it's still useful for air-gapped builds, supply-chain control, and forensics. The single biggest gotcha: **`vendor/` and `go.mod` must agree** — adding a dep without re-vendoring breaks the build. Always run `go mod tidy && go mod vendor` together.

## Mental Model

```
   Without vendoring (default):
       go build → consult go.mod → fetch from GOPROXY or cache → compile

   With vendoring:
       go build → consult vendor/modules.txt → read sources from vendor/ → compile
       (No network. No proxy. No checksum DB. Just files on disk.)

   project/
   ├── go.mod
   ├── go.sum
   ├── main.go
   └── vendor/
       ├── modules.txt              ← manifest: module versions present
       ├── github.com/x/y/         ← copied source
       │   └── ...
       └── golang.org/x/sync/      ← copied source
           └── ...
```

The vendor directory is conceptually a snapshot of the module cache, scoped to this project, committed to git. Build is deterministic without any network access.

## Syntax & Basic Usage

```bash
$ go mod vendor                 # generate vendor/ from go.mod
$ ls vendor/
github.com/x/y/   golang.org/x/sync/   modules.txt
$ go build ./...                # uses vendor/ by default if go.mod's `go` ≥ 1.14
```

Force vendor mode:

```bash
$ go build -mod=vendor ./...
```

Ignore vendor (use cache/proxy):

```bash
$ go build -mod=mod ./...
```

Verify the vendor matches `go.mod`:

```bash
$ go mod verify       # checks vendor/ + cached sources against go.sum
```

## Deep Dive

### History

- **Pre-1.5**: no official vendoring. People copied deps into `GOPATH` subdirectories.
- **1.5–1.10**: experimental `vendor/` directory support; flat structure under each module.
- **1.11+ (modules)**: `vendor/` survives but is no longer the primary mechanism.
- **1.14+**: vendor mode is auto-enabled when `vendor/` exists and `go.mod` says `go ≥ 1.14`.

The Go team's stance is that vendoring is a tool for specific use cases, not the default. The `vendor/` mechanism is supported but de-emphasized.

### `vendor/modules.txt`

```
# github.com/google/uuid v1.6.0
## explicit
github.com/google/uuid
# golang.org/x/sync v0.7.0
## explicit; go 1.18
golang.org/x/sync/errgroup
golang.org/x/sync/singleflight
# rsc.io/binaryregexp v0.2.0
rsc.io/binaryregexp
```

Generated by `go mod vendor`. Each module gets:

- A version line (`# <module> <version>`).
- An optional `## explicit` marker (the module is a direct dep, in `go.mod`'s `require` block without `// indirect`).
- An optional `## explicit; go <version>` (since 1.17 — records the dep's `go` directive).
- A list of *packages used* from that module — not the entire module's content, just the packages your code imports.

Selective vendoring (only used packages) keeps `vendor/` smaller. If you import `golang.org/x/sync/errgroup` but not `singleflight`, only `errgroup` is vendored... actually, since 1.17, all packages reachable in the module are vendored to support reflection and `go list`. The manifest still notes which are imported.

### Vendor mode auto-activation

Conditions:
1. A `vendor/` directory exists.
2. `vendor/modules.txt` exists.
3. `go.mod`'s `go` directive is ≥ 1.14.

If all three are true and no `-mod=...` flag is given, vendor mode is the default. Some tooling (especially older Bazel rules) force `-mod=vendor` explicitly.

### Verification

`go mod verify` checks each cached/vendored module against `go.sum`. If a vendor file has been edited:

```
verifying github.com/x/y@v1.2.3: dir has been modified
```

Use `go mod vendor -e` to regenerate if you intentionally edited (rare; almost always a bad idea).

### Vendor and `go.sum`

`go.sum` is still required. Vendor mode doesn't bypass checksum verification — the Go tool re-hashes vendored sources and compares to `go.sum`. Editing `vendor/` without updating `go.sum` causes verification failure.

### Disabling vendor

Three ways:

```bash
$ go build -mod=mod ./...              # this command only
$ rm -rf vendor                         # forever
$ go build -mod=readonly ./...          # like vendor=off but errors on go.mod changes
```

`-mod=readonly` is common in CI to detect "this build implicitly modified go.mod" (which would happen if a dep was missing).

### `vendor/`-related env vars

```
GOFLAGS=-mod=vendor    # force vendor mode for every command
GOFLAGS=-mod=mod       # force module-cache mode
```

Useful for shell or CI environment defaults.

### When vendoring is the right answer

1. **Air-gapped environments**: build hosts without internet access. Vendor everything; ship the repo.
2. **Reproducibility paranoia**: vendor is the absolute snapshot. The proxy and sumdb are highly reliable, but they're external services with availability concerns. Vendor cuts the cord.
3. **Supply-chain auditing**: code review every line of every dep before it ships. Vendor makes the audit boundary clear: it's whatever's in `vendor/`.
4. **Forensics**: when a bug shipped in production traces to a specific transitive dep, having that source in-tree at the released commit makes archeology trivial.
5. **Long-tail compatibility**: a dep's proxy entry could be retracted or removed; vendor preserves the source you actually shipped.
6. **CI/CD speed**: vendor builds skip the proxy round-trip and module-cache extraction. Saves seconds-to-minutes on cold builds.
7. **Some build systems**: Bazel `rules_go` historically preferred vendor for deterministic, sandboxed builds.

### When vendoring is the wrong answer

1. **Casual projects**: just use the module cache; it's already deterministic.
2. **Open-source libraries**: do NOT vendor in libraries you publish. Vendored sources confuse consumers (`go mod tidy` strips them, `go list` reports both versions of the same module).
3. **Massive dep trees**: `vendor/` for a project with 200+ transitive deps can be hundreds of MB. Git history bloats. Reviews on dep changes become unreadable.

### Cost analysis

| Cost | Without vendor | With vendor |
|---|---|---|
| Disk in repo | minimal | +100 MiB to GiB |
| Git history size | minimal | grows with every dep change |
| Cold-build time | proxy fetches (seconds) | local-only (faster) |
| Determinism | high (sumdb) | absolute |
| Network required | yes (for first build) | no |
| Visibility | proxy + cache | committed files |
| `go.sum` size | smaller | same |
| Audit boundary | `go.sum` + module cache | `vendor/` directory |

### Selective vs full vendoring

Some teams vendor only specific deps (e.g., only their security-critical chain) while leaving others to the proxy. This is *not* how `go mod vendor` works — it vendors everything in the build list. Manual partial vendoring is possible but breaks the `vendor/modules.txt` convention and reverts to old GOPATH-style copying. Not recommended.

### `go mod vendor` flags

```bash
$ go mod vendor -v              # verbose
$ go mod vendor -o ./vendor2    # different output dir (rare)
$ go mod vendor -e              # continue on errors
```

Pre-1.22, `go mod vendor` ignored `embed`-required files (like images, templates). Since 1.22, it copies them along with `.go` files. Verify with: do all `//go:embed` directives still resolve after `go mod vendor`? They should.

### vendor and tests

Vendor includes test files of imported packages. This is sometimes a source of bloat (test fixtures, large fixture binaries vendored unnecessarily). 1.22+ has fewer such cases; older versions sometimes vendored multi-MB testdata.

### Cross-platform builds

Vendor copies *every file* regardless of build constraints. A `vendor/foo/bar_windows.go` will be present on Linux builds; the Go tool ignores it via build constraints. This is correct but bloats `vendor/`.

### CI patterns

```yaml
- name: Verify vendor
  run: |
    go mod vendor
    git diff --exit-code vendor/ go.mod go.sum
```

If a contributor changed deps without vendoring, CI fails. Pair with `go mod tidy` check.

```yaml
- name: Build offline
  run: |
    export GOFLAGS="-mod=vendor"
    export GOPROXY=off       # ensure no network access
    go build ./...
```

The second job verifies the vendor is complete by building with no proxy. Catches "I forgot to add a transitive dep to vendor" bugs.

### Vendored cgo dependencies

cgo glue files (`.c`, `.h`, `.s`) are vendored too. Their compilation requires the platform's C toolchain at build time; vendoring doesn't change that. Cross-compilation with vendored cgo is the same pain as without.

### Vendor across modules

In a workspace (`go.work`), vendor is per-module: each `use`'d module can have its own `vendor/`. Workspace mode generally disables vendor (`go build` ignores `vendor/` in workspace context; force with `-mod=vendor`).

For a single-module monorepo, `vendor/` is at the repo root and covers everything.

## Standard Library Hooks

- `go mod vendor` — generate.
- `go build -mod=vendor` / `-mod=mod` / `-mod=readonly`.
- `GOFLAGS=-mod=vendor` — env-level default.
- `go mod verify` — re-hash and compare.
- `vendor/modules.txt` — manifest.
- `go.sum` — hashes (still required in vendor mode).
- `runtime/debug.ReadBuildInfo` — records `-mod=vendor` build setting.

## Real-World Patterns

### 1. Vendor for an air-gapped build

```bash
# On a network-connected machine:
$ go mod tidy
$ go mod vendor
$ git add vendor/ go.mod go.sum
$ git commit -m "vendor deps for offline build"

# On the air-gapped build host:
$ git pull
$ go build -mod=vendor ./...
# No network needed; succeeds.
```

### 2. CI parallel jobs: with-vendor + without-vendor

```yaml
jobs:
  module-mode:
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
      - run: go test -mod=mod ./...
  vendor-mode:
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
      - env: { GOPROXY: off }
        run: go test -mod=vendor ./...
```

Module mode validates `go.mod`; vendor mode validates `vendor/` completeness.

### 3. Detect vendor drift

```bash
$ go mod vendor
$ git status --porcelain vendor/
M  vendor/github.com/x/y/y.go
```

If anything's modified, the vendor doesn't match `go.mod`. Either re-vendor or revert.

### 4. Selective audit

```bash
# Before each release: review only what changed in vendor
$ git diff v1.2.0..HEAD -- vendor/
```

When vendor is committed, dep changes are visible in PRs. Some teams require code review of vendor-diff changes alongside the `go.mod` bump.

### 5. Strip vendor for a release artifact

For published libraries, do **not** include `vendor/`. If you have it locally for testing:

```bash
$ rm -rf vendor/
$ go test ./...    # works against module cache
$ git tag v1.5.0
$ git push --tags
# The tag doesn't include vendor/.
```

Some teams `.gitignore` `vendor/` from the start for libraries; only applications vendor.

## Anti-Patterns & Gotchas

**Vendoring a library you publish.** Consumers' tooling assumes a clean tree. Your `vendor/` confuses `go.sum` resolution downstream. Don't.

**Editing files in `vendor/` to "fix" a dep.** Future `go mod vendor` blows it away. Use `replace` to a fork instead.

**Vendor without committing `go.sum`.** They pair. Both committed or neither.

**Forgetting to re-vendor after dep changes.** CI will catch it; develop the habit anyway.

**Using `vendor/` to skip `go mod tidy`.** Vendor mode doesn't tidy; you still need a tidy `go.mod`.

**Hand-pasting code into `vendor/`.** Not vendoring; just copying. The Go tool can't track such code via modules.

**Vendoring a private module without checking auth.** `go mod vendor` runs as-the-user; if your `GOPRIVATE` and credentials are set up, it works. CI often has different auth.

**Massive `vendor/` in code review.** Several thousand-line vendor diffs per PR drown reviewers. Either review separately or use a CI bot to summarize.

**Treating vendor as a security mechanism.** It's a snapshot, not a sandbox. A vendored malicious dep is still malicious. Use govulncheck against the build list.

**Mixing `-mod=vendor` and modifying `go.mod` in the same workflow.** Vendor mode is conceptually read-only on dep state. Resolve with `-mod=mod` for changes, then re-vendor.

**Believing `vendor/` substitutes for `GOPRIVATE`.** Vendor builds skip the proxy, but the initial `go mod vendor` still hits it. For fully private modules, configure `GOPRIVATE` first.

## Performance Notes

- Cold build with proxy: 30 s – 2 min (network + extraction).
- Cold build with vendor: 5–30 s (local file read).
- Warm cache (proxy or vendor): roughly equivalent; both build from local files.
- `go mod vendor` cost: O(deps × file count); ~10 s for 100 deps.
- Vendor disk usage: 100 MiB – 1 GiB typical; >5 GiB for huge codebases.
- Git operations on big `vendor/`: clone/checkout time scales with vendor size.

## How Big Companies Use It

- **Kubernetes** vendors all its deps: https://github.com/kubernetes/kubernetes/tree/master/vendor.
- **Docker / Moby** has vendored since pre-modules days; modernized to `go mod vendor`: https://github.com/moby/moby.
- **HashiCorp Vault / Consul / Nomad / Terraform** all vendor for reproducibility and offline builds: https://github.com/hashicorp/vault.
- **etcd** vendors for build determinism in CNCF release pipelines: https://github.com/etcd-io/etcd.
- **CockroachDB** vendors and uses a custom tool to detect drift: https://github.com/cockroachdb/cockroach.
- **Cilium** vendors for kernel-side eBPF dep stability: https://github.com/cilium/cilium.
- **Google internal Go** uses a vendor-like mechanism via Blaze/Bazel for hermetic builds.
- **CNCF release process** generally requires that releases be reproducible from a single source archive — vendor makes this easy.
