# Mocking Strategies — Interfaces, `gomock`, `mockery`

## TL;DR

Go has no language-level mock support. The community has settled on three patterns: **(1) hand-rolled fakes** behind small interfaces (the "Go way" — accept interfaces, return structs), **(2) gomock** (now `go.uber.org/mock`) which generates type-checked mocks from interface declarations via `mockgen` plus a runtime expectation API, **(3) mockery** (community) which generates `testify/mock`-flavored mocks. The most important design rule is upstream of the choice: **define interfaces at the call site** (the consumer), not at the implementation. Then your code under test depends on a tiny interface, and you can swap in a hand-rolled fake or a generated mock as needed. Hand-rolled fakes win for simplicity and clarity; gomock/mockery win for large surfaces where strict expectation checking pays off. Most codebases use both — hand-rolled for small interfaces, generated for big ones.

## Mental Model

```
   Consumer (your code)         Interface           Implementation
   service.go                   Store               PostgresStore
       func New(s Store) ...    type Store interface {
                                    Get(id) (User, error)
                                    Put(u User) error
                                }

   In tests:
        Store ────► fakeStore{}       ──── hand-rolled
                ────► MockStore{}      ──── generated by gomock
                ────► mockery.Store{}  ──── generated by mockery
```

The interface is owned by the consumer; the implementation satisfies it implicitly. Mocking strategy is a downstream choice.

## Syntax & Basic Usage

```go
// 1. Hand-rolled fake
type fakeStore struct { users map[string]User }
func (f *fakeStore) Get(id string) (User, error) {
    u, ok := f.users[id]; if !ok { return User{}, ErrNotFound }; return u, nil
}
func (f *fakeStore) Put(u User) error { f.users[u.ID] = u; return nil }

// 2. gomock generation
//go:generate go run go.uber.org/mock/mockgen -source=store.go -destination=mock/mock_store.go -package=mock

// 3. mockery (config-driven .mockery.yaml then run mockery)
```

In tests:

```go
s := &fakeStore{users: map[string]User{"42": {ID: "42", Name: "alice"}}}   // hand-rolled

ctrl := gomock.NewController(t)                                              // gomock
s := mock.NewMockStore(ctrl)
s.EXPECT().Get("42").Return(User{ID: "42", Name: "alice"}, nil)

s := mocks.NewStore(t)                                                       // mockery
s.EXPECT().Get("42").Return(User{ID: "42"}, nil)
```

## Deep Dive

### "Accept interfaces, return structs"

Idiomatic Go: a consumer declares the minimum interface it needs; the implementation returns a concrete type.

```go
// store/postgres.go
type PostgresStore struct{ db *sql.DB }
func New(db *sql.DB) *PostgresStore { ... }
func (s *PostgresStore) Get(id string) (User, error) { ... }
func (s *PostgresStore) Put(u User) error { ... }

// service/user.go
type userGetter interface { Get(id string) (User, error) }   // only what we need
type UserService struct { store userGetter }
func NewUserService(s userGetter) *UserService { ... }
```

The consumer's interface (`userGetter`) is tiny, and the test only mocks `Get`. No need to mock `Put` if `UserService` doesn't call it.

### Hand-rolled fakes

Pros: zero dependencies, easy to read, per-test customization via function fields.
Cons: manual boilerplate for big interfaces, no expectation framework.

```go
type fakeUserGetter struct { GetFunc func(id string) (User, error) }
func (f *fakeUserGetter) Get(id string) (User, error) { return f.GetFunc(id) }

func TestService(t *testing.T) {
    f := &fakeUserGetter{GetFunc: func(id string) (User, error) {
        return User{ID: id, Name: "alice"}, nil
    }}
    svc := NewUserService(f)
    // ...
}
```

### `gomock` (now `go.uber.org/mock`)

Generates type-checked mocks. Legacy `github.com/golang/mock` is archived; current is **`go.uber.org/mock`** (Uber maintains the fork).

```bash
$ go install go.uber.org/mock/mockgen@latest
$ mockgen -source=store.go -destination=mock/mock_store.go -package=mock
```

Usage:

```go
ctrl := gomock.NewController(t)   // auto-finalize since v1.5
m := mock.NewMockStore(ctrl)
m.EXPECT().Get("42").Return(User{ID: "42"}, nil)
m.EXPECT().Put(gomock.Any()).Return(nil).Times(2)
svc := NewUserService(m)
```

Features: strict expectations, rich matchers (`gomock.Any`, `Eq`, `AssignableToTypeOf`), times constraints, order constraints (`gomock.InOrder`, `c1.After(c2)`), `DoAndReturn` for dynamic responses.
Drawbacks: generates a lot of code, DSL has a learning curve, strict expectations can be brittle.

### `mockery`

Uses `testify/mock` as the base. Config-driven (`.mockery.yaml`):

```yaml
with-expecter: true
packages:
  github.com/me/proj/store:
    interfaces: { Store: {} }
```

```go
s := mocks.NewStore(t)
s.EXPECT().Get("42").Return(User{ID: "42"}, nil).Once()
```

Features: cleaner API than testify's raw `mock`, auto-cleanup via `NewStore(t)`, less strict than gomock by default.
Drawbacks: depends on testify (`10-testing/12-testify-controversy.md`), v3 broke v2 API.

### Comparison

| Aspect              | Hand-rolled | gomock           | mockery     |
|---------------------|-------------|------------------|-------------|
| Setup cost          | Zero        | mockgen + gen    | mockery + cfg |
| Per-test code       | More        | Less (DSL)       | Less (DSL)  |
| Argument matching   | Manual      | Rich             | Rich        |
| Strict expectations | Manual      | Default          | Opt-in      |
| Generated code      | None        | Lots             | Lots        |
| Dep footprint       | Zero        | go.uber.org/mock | testify     |

### When to hand-roll

Interface has 1–3 methods; test scenarios obvious from setup data; zero deps in test path; interface changes often.

### When to generate

Interface has 10+ methods; you want compile-time errors on mocks when the interface changes; you want call-order assertions; team is comfortable with a mocking DSL.

### Fake server pattern

For HTTP clients, prefer `httptest.NewServer` (`10-testing/08-httptest.md`) over mocking `http.Client`. Real HTTP calls catch more bugs than mock interfaces.

### In-memory implementation pattern

```go
type Store interface { Get(id) (User, error); Put(User) error }
type MemoryStore struct { mu sync.Mutex; users map[string]User }
type PostgresStore struct { db *sql.DB }
```

Both satisfy `Store`. Less brittle than mocks because in-memory has real behavior (insertions persist, gets reflect prior puts, etc.).

### Mocking `time.Now`

```go
type Clock interface { Now() time.Time }
type RealClock struct{}; func (RealClock) Now() time.Time { return time.Now() }
type FakeClock struct{ T time.Time }; func (c FakeClock) Now() time.Time { return c.T }
```

Or use `testing/synctest` (Go 1.24+) for synthetic time without an interface (`10-testing/13-testing-synctest.md`).

### Mocking `context.Context`

Don't. Use `context.Background()` or `context.WithCancel`.

### Mocking `io.Reader`/`io.Writer`

Stdlib has helpers in `testing/iotest`: `OneByteReader`, `ErrReader`, `DataErrReader`. For ad-hoc fakes:

```go
type errReader struct{}
func (errReader) Read(_ []byte) (int, error) { return 0, errors.New("forced") }
```

### Mock interface bloat

A 20-method interface is a smell. Split into Reader/Writer/Admin etc. Tests only mock what they use.

### Mocking the database

Three options:

1. **Mock the SQL driver** with `go-sqlmock` — brittle (mock query strings).
2. **In-memory SQL** with SQLite (`modernc.org/sqlite` for pure Go) — more accurate but dialect differs.
3. **Real DB via testcontainers-go** (`10-testing/10-integration-tests.md`) — most accurate but slowest.

Pick per layer: domain logic → mocks; query logic → SQLite or testcontainers.

### Static dispatch alternative: function fields

```go
type Service struct {
    Now  func() time.Time
    UUID func() string
}
func (s *Service) Tick() Event { return Event{ID: s.UUID(), Time: s.Now()} }
```

Production: `s.Now = time.Now`. Test: `s.Now = func() time.Time { return testTime }`. Lighter than an interface; great for cross-cutting helpers.

## Real-World Patterns

### 1. Hand-rolled minimal

```go
type stubAuth struct{ token string }
func (s stubAuth) Verify(t string) bool { return t == s.token }
```

### 2. gomock-style

```go
//go:generate mockgen -source=auth.go -destination=mock_auth.go -package=auth
ctrl := gomock.NewController(t)
m := NewMockAuth(ctrl)
m.EXPECT().Verify("abc").Return(true)
```

### 3. mockery v3

```go
m := mocks.NewAuth(t)
m.EXPECT().Verify("abc").Return(true).Once()
```

### 4. In-memory implementation

```go
type MemCache struct { mu sync.Mutex; m map[string]string }
func NewMemCache() *MemCache { return &MemCache{m: map[string]string{}} }
```

### 5. Function fields

```go
type Foo struct { Sleep func(time.Duration) }
func (f *Foo) Backoff() { f.Sleep(time.Second) }
```

### 6. Real HTTP server (preferred over mock client)

```go
srv := httptest.NewServer(http.HandlerFunc(...))
defer srv.Close()
c := NewClient(srv.URL)
```

### 7. SQL mock

```go
db, mock, _ := sqlmock.New()
mock.ExpectQuery("SELECT").WillReturnRows(sqlmock.NewRows([]string{"id"}).AddRow(1))
```

(Brittle — prefer in-memory SQLite or testcontainers.)

## Anti-Patterns & Gotchas

**Defining interfaces at the implementation side.** Forces consumers to import the implementation just to declare a mock. Define at the consumer.

**Huge interfaces.** A 30-method mock is unmaintainable. Split.

**Mocking value-objects (`time.Time`, `context.Context`).** Use real values or controlled clocks.

**Over-specified expectations (`gomock.InOrder` for everything).** Test becomes brittle; refactors that shouldn't change semantics fail. Specify only what matters.

**Mocking the HTTP client.** Easy to mock the request; hard to mock the full transport behavior (redirects, retries, TLS). Prefer `httptest.NewServer`.

**Mocking the SQL driver string queries.** Tests check query *text* equality; trivial refactors break. Prefer in-memory DB or integration tests.

**Mixing gomock and mockery in one repo.** Two DSLs to learn. Pick one.

**Forgetting to call `ctrl.Finish()`.** Pre-gomock-v1.5, expectations were never verified. Modern gomock auto-finalizes via `t.Cleanup`.

**Hand-rolled fakes with no behavior (always return `nil, nil`).** Misses real bugs. Test should care about realistic state.

**Mocking `time.Now` via interface when `testing/synctest` exists.** 1.24+ teams should reach for synctest first.

**Mocking everything in sight.** Some teams mock all deps "for purity". Result: tests pass while production crashes. Use mocks for *external* dependencies (network, DB); use real internal types.

**Generated mocks committed to the implementation package.** Creates import cycles for tests. Generate into a separate `mock/` subpackage.

## Performance Notes

- Hand-rolled fakes: nanosecond overhead.
- gomock dispatch: ~100ns per call.
- mockery dispatch: similar.
- Mock generation: 1–5s per package (one-time, then cached).
- In-memory implementations: as fast as the data structures.

Test latency rarely dominated by mocking; it's the I/O you avoided that matters.

## How Big Companies Use It

- **Google** uses hand-rolled fakes + gomock; gomock originated at Google: https://github.com/google/wire.
- **Uber** maintains the current gomock fork (`go.uber.org/mock`): https://github.com/uber-go/mock.
- **Kubernetes** uses interfaces + hand-rolled fakes + `client-go`'s fake clients: https://github.com/kubernetes/kubernetes.
- **HashiCorp** uses mockery in some Terraform code, hand-rolled in others: https://github.com/hashicorp/terraform.
- **CockroachDB** uses hand-rolled mocks plus in-memory test variants: https://github.com/cockroachdb/cockroach.
- **Tailscale** uses hand-rolled fakes universally; no gomock/mockery: https://github.com/tailscale/tailscale.
- **Discord** uses mockery v3 for their large interfaces.

## Exercises / Self-Check

1. Pick an interface in your code with 10+ methods. Could it be split? Sketch the smaller interfaces.
2. Convert one gomock test to a hand-rolled fake. Is it easier or harder to read?
3. Mock `time.Now` via interface. Then replace with `testing/synctest` (if on 1.24+). Compare both.
4. Replace a `go-sqlmock`-based test with an in-memory SQLite. Compare maintainability.
5. Use `httptest.NewServer` instead of mocking `*http.Client`. Were any bugs caught that the mock wouldn't have?
