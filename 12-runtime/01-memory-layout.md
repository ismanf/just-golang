# Runtime Memory Layout — mheap, mcentral, mcache, mspan

## TL;DR

Go's allocator is a **TCMalloc descendant**: a global page heap (`mheap`) carved into spans (`mspan`), each span sized to hold many objects of one size class. Per-P caches (`mcache`) hand out objects without locks; per-size-class central lists (`mcentral`) refill the caches; the heap reserves and returns OS memory in arenas of 64 MiB on Linux/amd64. The single biggest gotcha: allocations ≥32 KiB skip the cache and go straight to `mheap` — sizing decisions can flip an object between two completely different fast paths. Spans, not objects, are the unit the GC sweeps and the OS returns.

## Mental Model

```
                    +---------------------+
                    |    OS (mmap arenas) |   64 MiB arenas (linux/amd64)
                    +----------+----------+
                               |
                    +----------v----------+
                    |       mheap         |   global, lock-protected
                    |  (free spans, by    |
                    |   page count)       |
                    +----------+----------+
                               |
                  +------------+------------+
                  |                         |
        +---------v--------+      +---------v--------+
        | mcentral (class  |      | mcentral (class  |
        |    1: 8B objs)   |      |   67: 32 KiB)    |   one per size class
        | partial / full   |      | partial / full   |   (2 per class: scan/noscan)
        +---------+--------+      +---------+--------+
                  |                         |
        +---------v--------+      +---------v--------+
        |  mcache (P0)     |      |  mcache (P1)     |   per-P, lock-free
        |  alloc[68][2]    |      |  alloc[68][2]    |
        +------------------+      +------------------+
                  |                         |
                  v                         v
            user objects               user objects
```

A span (`mspan`) is a run of consecutive 8 KiB pages dedicated to one size class. Class 1 = 8-byte objects; class 67 = 32 KiB. There are 68 small size classes (0 is reserved). Each class has two `mcentral` lists: one for spans containing pointer-bearing ("scan") objects, one for pointer-free ("noscan"). The split lets the GC skip scanning halves of memory.

## Syntax & Basic Usage

Allocator behavior is implicit — you don't call it. But you can observe it:

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("HeapAlloc = %d KiB\n", m.HeapAlloc/1024)
	fmt.Printf("HeapSys   = %d KiB (reserved from OS)\n", m.HeapSys/1024)
	fmt.Printf("HeapIdle  = %d KiB (in spans, not in use)\n", m.HeapIdle/1024)
	fmt.Printf("HeapInuse = %d KiB (in spans, in use)\n", m.HeapInuse/1024)
	fmt.Printf("NumGC     = %d\n", m.NumGC)
}
```

`HeapInuse - HeapAlloc` is fragmentation inside spans. `HeapIdle - HeapReleased` is memory the runtime is holding for reuse but hasn't given back to the OS.

## Deep Dive

### Size classes

The set of size classes is generated by `cmd/compile/internal/sizeclass/mksizeclasses.go`. The classes are chosen so that internal waste per span stays under 12.5%. The full table lives in `runtime/sizeclasses.go` and looks like:

```
// class  bytes/obj  bytes/span  objects  tail waste  max waste
//     1          8        8192     1024           0     87.50%
//     2         16        8192      512           0     43.75%
//     3         24        8192      341           8     29.24%
//    ...
//    67      32768       32768        1           0     12.50%
```

`MaxSmallSize = 32768`. Anything larger is a "large" allocation: it gets its own dedicated span sized to fit. The cutoff matters: at 32 KiB + 1 byte the allocator path branches into a different code path (`mallocgc -> largeAlloc`).

### mcache — per-P, lockless

```go
// runtime/mcache.go (excerpt; BSD-3 © The Go Authors)
type mcache struct {
    nextSample int64
    scanAlloc  uintptr
    tiny       uintptr // tiny allocator base
    tinyoffset uintptr
    tinyAllocs uintptr
    alloc      [numSpanClasses]*mspan // current span by spanClass
    ...
}
```

`alloc` is indexed by *spanClass*, which encodes both the size class and the scan/noscan bit: `spanClass = sizeclass<<1 | noscan`. For 68 classes that's 136 entries. The current span is just a free-list pointer; allocation is "bump the freelist".

Because the cache is per-P, no lock is needed. When the current span runs out, the cache calls `refill` which grabs a fresh span from the matching `mcentral`.

### mcentral — per-class spans

```go
// runtime/mcentral.go (excerpt; BSD-3 © The Go Authors)
type mcentral struct {
    spanclass spanClass
    partial   [2]spanSet // spans with free objects
    full      [2]spanSet // spans with no free objects
}
```

The `[2]` dimension is for GC: one entry holds spans the GC has finished sweeping in this cycle, the other holds spans yet to sweep. The mcache asks the central for a partial span; if there are none, the central asks the mheap for a fresh page run and carves it.

### mheap — page-granularity

```go
// runtime/mheap.go (excerpt; BSD-3 © The Go Authors)
type mheap struct {
    lock      mutex
    pages     pageAlloc
    allspans  []*mspan
    central   [numSpanClasses]struct {
        mcentral mcentral
        pad      [...]byte // cache-line padding
    }
    ...
}
```

The page allocator (`pageAlloc` in `runtime/mpagealloc.go`) is a radix-tree bitmap allowing O(log n) "find N free contiguous pages". Pre-1.14 this was a treap and a major source of GC latency; the radix bitmap design was a complete rewrite that removed lock contention from large allocations.

### Arenas

Memory is requested from the OS in **arenas** (64 MiB on linux/amd64; 4 MiB on 32-bit). Arenas are reserved with `mmap(PROT_NONE)` and committed (`mmap(PROT_READ|PROT_WRITE)`) on demand. An arena's page metadata (a `heapArena` struct) is also allocated lazily.

```
            arena 0 (64 MiB)              arena 1 (64 MiB)            ...
            [ pages... ][ pages... ]      [ pages... ]

            metadata for each arena:
              - bitmap: 1 bit per pointer-word ("is pointer?")
              - pageMarks, pageInUse, pageSpecials
```

The "is pointer" bitmap (1 byte per pointer-sized word on amd64) is what the GC scanner consults; it's why `noscan` objects (no pointer-bearing words) need no scanning at all.

As of Go 1.22+ the heap arena bitmap is replaced by **per-type GC bitmaps stored alongside the allocation** for small types, eliminating the global bitmap for those — see the [Go 1.22 release notes](https://go.dev/doc/go1.22) and `runtime/mbitmap.go`.

### Tiny allocator

Objects ≤16 bytes with no pointers (`tinyAllocs`) are packed into a single "tiny block". A tiny block is itself a 16-byte allocation from class 2; the cache tracks `tinyoffset` and bumps it for each call. This avoids per-object overhead for things like small `string` headers in some pipelines. See `mallocgc` in `runtime/malloc.go`.

### Allocation path summary

```
mallocgc(size, type, needzero) →

  if size <= maxTinySize (16) && noscan:
      bump in tiny block

  elif size <= 32768:
      class = size_to_class[size]
      span  = mcache.alloc[spanclass]
      if span.freelist == nil:
          refill from mcentral
      bump freelist pointer

  else:
      directly allocate span from mheap
```

### Span states

A span is in one of:
- `mSpanDead` — not in use
- `mSpanInUse` — handed out to a cache
- `mSpanManual` — used by runtime itself (stack spans, work bufs)

Transitions are bracketed by `mheap.lock`.

### MADV_DONTNEED vs MADV_FREE

When the scavenger returns pages to the OS it uses `madvise(MADV_DONTNEED)` on Linux (since 1.16; earlier `MADV_FREE`) so RSS visibly drops. `MADV_FREE` had two operational problems: tools (top, RSS counters) didn't reflect the release, and pages were taken back lazily — a noisy neighbour could hold memory until *real* pressure. `DONTNEED` fixes both at the cost of slightly more page faults on reclaim.

You can toggle via env: `GODEBUG=madvdontneed=0` (default 1 since 1.16).

### Soft memory limit (since 1.19)

`debug.SetMemoryLimit` lets you cap total Go-managed memory; the GC accelerates as you approach the limit. Allocator behavior changes slightly: when `live + reserved > softLimit`, the runtime will refuse to grow the heap and force GC instead. See `12-runtime/04-gc-tuning.md`.

## Standard Library Hooks

- `runtime.MemStats` (`runtime.ReadMemStats`) — comprehensive heap counters. Stop-the-world cost; ~100 µs–ms.
- `runtime/metrics` (since 1.16) — non-stop-the-world counters; preferred for monitoring.
- `runtime/debug.FreeOSMemory()` — force scavenger to release memory now.
- `runtime/debug.SetMemoryLimit(n int64)` — soft limit (since 1.19).
- `GODEBUG=allocfreetrace=1` — log every alloc/free with stack. Useful for tiny reproducers, ruinous for real workloads.
- `GODEBUG=gctrace=1` — per-GC summary including heap sizes.
- `GODEBUG=madvdontneed=0` — opt back into `MADV_FREE`.
- `GODEBUG=scavtrace=1` — trace scavenger activity.

## Real-World Patterns

### 1. Pre-size the allocation to avoid span churn

```go
package main

import "fmt"

func main() {
	// Bad: starts capacity 0, regrows to ~512.
	bad := []byte{}
	for i := 0; i < 500; i++ {
		bad = append(bad, byte(i))
	}

	// Good: one span allocation, predictable class (class 7, 128 bytes).
	good := make([]byte, 0, 500)
	for i := 0; i < 500; i++ {
		good = append(good, byte(i))
	}
	fmt.Println(len(bad), len(good))
}
```

Growing through `append` triggers reallocations that bump the slice's size class up the table — each step changes the span class. Pre-sizing pins it.

### 2. Use noscan types where you can

If a struct is "all-bits" (no pointers, no maps, no interfaces, no chans), it goes to a noscan span. The GC never touches it. Storing 100 MiB of `[]uint64` is ~free GC-wise; storing 100 MiB of `[]*Node` is not.

```go
package layout

type RowPtr struct { // scan span — GC visits every pointer
	Key  *string
	Vals *[]int64
}

type RowFlat struct { // noscan span — invisible to GC
	Key  [32]byte
	Vals [16]int64
}
```

Trading struct flexibility for noscan-ness is a common move in latency-sensitive code (databases, caches).

### 3. Observe span behavior

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)

	keep := make([][]byte, 0, 10000)
	for i := 0; i < 10000; i++ {
		keep = append(keep, make([]byte, 200)) // class 13, 224 bytes
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("alloc bumped: %d KiB\n", (m2.HeapAlloc-m1.HeapAlloc)/1024)
	fmt.Printf("spans in use: %d -> %d\n", m1.HeapInuse, m2.HeapInuse)
	_ = keep
}
```

The 200-byte ask is rounded to class 13's 224 bytes — the difference is internal waste. Multiply by 10000.

### 4. Force return to OS

```go
package main

import "runtime/debug"

func main() {
	debug.FreeOSMemory() // synchronously runs scavenger + sweep
}
```

Used after large transient workloads (batch jobs, bulk imports) to drop RSS immediately. Almost never needed in steady-state servers; the scavenger does this automatically.

## Anti-Patterns & Gotchas

**Assuming `len(s) == n` means n bytes allocated.** The allocator rounds up to the size-class boundary. `make([]byte, 17)` allocates 24 bytes (class 3).

**Hoping `runtime.GC()` will release memory to the OS immediately.** GC frees Go heap; the *scavenger* (background goroutine) returns it. Use `debug.FreeOSMemory()` if you need synchronous release.

**Treating `HeapAlloc` as RSS.** `HeapAlloc` is live, in-use Go heap. RSS includes spans-but-empty (HeapIdle - HeapReleased), runtime metadata, stacks, and any cgo/system allocations.

**Slabbing tiny structs into a `[]any`.** Each `any` is a 16-byte interface header *plus* a heap allocation for the underlying value (unless it fits a special case). 1M ints stored as `[]any` is ~32 MiB plus 1M tiny allocs vs 8 MiB for `[]int`.

**Pinning live memory in a sync.Pool that's not pressured.** `sync.Pool` is cleared at GC; if your workload never pressures GC, the pool grows. See `07-concurrency/06-sync-map-pool.md`.

**Profiling allocator without `-gcflags=-m`.** Escape analysis output tells you *why* an allocation is happening before the allocator sees it; reading the profile without it is half the picture.

**Conflating spans and pages.** A span is *N* contiguous pages; a "small" span is 1 page. Page count grows with object size.

**Expecting `MADV_FREE` semantics under `madvdontneed=1`.** Pages are gone — re-touching them faults them back. Hot loops that fault scavenged memory show RSS oscillation in monitoring; tune with `GODEBUG=scavtrace=1`.

## Performance Notes

- mcache hit (fast path): ~10 ns including type bitmap setup.
- mcache refill (mcentral): ~µs, lock contention rare due to per-P caches.
- mheap allocation (>32 KiB or refill miss): ~µs–10s of µs, depending on whether pages are free.
- Span sweep (per span, in GC): ~hundreds of ns.
- ReadMemStats: stops the world; 50–500 µs typical.
- runtime/metrics sample: ~µs, no stop-the-world.
- Tiny allocator hit rate of ~30% is typical for string-heavy code.
- Internal waste budget: ≤12.5% per class by design.

`go test -bench=. -benchmem` exposes alloc count and bytes per op; `pprof -alloc_objects` and `-alloc_space` slice the heap by site.

## How Big Companies Use It

- **Discord** rewrote a hot service from Go to Rust partly because of GC pause spikes that traced back to scan-heavy heap layouts; their post is the canonical "what happens when your spans are pointer-dense" cautionary tale: https://discord.com/blog/why-discord-is-switching-from-go-to-rust.
- **Dgraph / Badger** uses arenas of `[]byte` and value pointers to keep most data in noscan spans; the design is documented at https://dgraph.io/blog/post/badger-3/.
- **Tailscale** uses `sync.Pool` extensively to reuse spans; Brad Fitzpatrick's GopherCon talks describe the pattern.
- **CockroachDB** wrote a custom slab allocator on top of `[]byte` to skip the Go allocator entirely for hot per-RPC objects: https://www.cockroachlabs.com/blog/the-cost-of-allocation/.
- **Uber's `automaxprocs` and ZapLogger** both lean on size-class awareness — Zap's `Buffer` defaults to 1 KiB (class 21) and grows in power-of-two steps that stay aligned to class boundaries.
- **YouTube ad bidder** (Google internal, mentioned in Austin Clements' GopherCon 2018 talk) saw 30% RSS reduction after migrating to noscan layouts.
